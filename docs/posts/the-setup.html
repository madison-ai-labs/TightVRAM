The machine

A gaming PC turned headless inference server. Nothing about it is special, and that’s why it’s worth writing about.

Part What it is
GPU RTX 3070, 8 GB GDDR6, headless, so all 8 GB are usable
Link PCIe 3.0 x16. The card could do Gen4, the Comet Lake CPU can’t
CPU Intel Core i9-10850K, 10 cores / 20 threads
RAM 2 × 16 GB DDR4 (Corsair CM4X16GD3000C16), single rank, dual channel
OS Ubuntu 26.04, headless
Software llama.cpp built from source, CUDA 12.4, driver 595

The model is Qwen3.6-35B-A3B in Unsloth’s UD-Q4_K_XL quant: 22.4 GB on disk, 40 layers, a hybrid of Gated DeltaNet and full attention (only every fourth layer has a KV cache), and a mixture of experts with 256 experts per layer, 8 of which are active per token. As a control we ran Qwen3.5-9B Q4_K_M (5.7 GB), which fits entirely in VRAM.

Why this works at all

An MoE model of this size has about 18.8 GB of routed experts and about 2 GB of everything else. llama.cpp’s --n-cpu-moe N keeps the expert tensors of the first N layers in system RAM. Attention, the KV cache, the router and the shared expert stay on the card.

That changes what each phase costs:

  • Generation (tg): each token touches 8 of 256 experts per layer. The CPU computes them directly from RAM. Nothing crosses PCIe.
  • Prompt processing (pp): a batch of thousands of tokens touches nearly all experts. For batches of 32 tokens and up, llama.cpp copies the experts to the GPU and computes there, once per micro-batch (ubatch).

Keep these two paths in mind. Every later post is about one of them.

The first sweep

llama-bench with -ngl 99 -fa on -t 10, 5 repetitions, every configuration in its own process so an out-of-memory error doesn’t take down the run. A probe grid first found the Pareto points: each layer of experts on the GPU costs about 464 MiB, so the micro-batch you can afford depends on how many layers you push to the CPU. ub 2048 needs nc ≥ 34, ub 4096 needs nc ≥ 38, ub 8192 never fits.

n-cpu-moe ubatch pp512 pp4096 pp16384 tg128
32 1024 335 556 545 36.4
34 2048 319 908 891 33.2
38 4096 291 1,364 1,340 32.8
40 4096 285 1,339 1,309 31.2

t/s, mean of 5 runs, KV f16, XMP still off. Standard deviations were 0.1–9 t/s.

Why the micro-batch matters this much

The experts are streamed to the GPU once per ubatch, regardless of how many tokens are in it. We confirmed it with the memory controller’s own counters (perf stat -e uncore_imc/data_reads/), taking the slope over prompt length so warm-up doesn’t count:

ubatch time per ubatch RAM read per ubatch RAM written per ubatch traffic for a 16k prompt
1024 1.86 s 28.9 GB 14.2 GB 699 GB
2048 2.17 s 31.4 GB 15.5 GB 384 GB
4096 2.72 s 33.4 GB 16.5 GB 210 GB

Four times as many tokens per ubatch cost only 16 % more reads. A 16k prompt at ub 1024 moves 699 GB through the memory controller. At ub 4096 it moves 210 GB.

Two things in that table didn’t add up yet. Reads are 1.5–1.7× the size of all experts (19.7 GB), and there are writes at all. We wrote it down as unexplained. The answer came a day later, in the post about pinned memory.

Short prompts can’t amortize anything: pp512 stays at 285–335 t/s in every configuration. An agent turn that adds 1,500 tokens to a cached prefix pays the full streaming cost. That makes the prompt cache the most important feature for agent workloads, and it works: in a replay of a real agent session, follow-up turns recomputed only 1.3–1.5k of ~20k tokens.

KV cache: f16 stays

Because only 10 of 40 layers have a KV cache, its type doesn’t change speed. Differences of ±2 t/s in tg turned out to be noise between processes (more on that in the next post). Quality does change, measurably:

wikitext-2, 8 × 4096 tokens
Perplexity f16 / q8_0 5.8456 / 5.8555 (+0.17 % ± 0.08 %)
Mean KL divergence 0.0031 (99th percentile 0.031, max 0.29)
Same top token 97.86 %

No speed for a measurable quality cost. q8_0 only makes sense if the context doesn’t fit otherwise.

How much context fits

Configuration VRAM after start
nc 38, ub 4096, f16, 64k 6.2 GB ok
nc 38, ub 4096, f16, 128k OOM, compute buffer 2.1 GB
nc 40, ub 4096, f16, 128k 7.0 GB chosen
nc 36, ub 2048, f16, 128k 7.8 GB too tight

At ub 4096 the largest context that starts is 155,648 tokens. That run filled to 149k tokens, prefilled at 1,047 t/s and left 62 MiB free. We stayed at 128k with 734 MiB of headroom. A smaller ubatch would buy more context (213k at ub 2048, 229k at ub 1024), but every long document would take 1.5–2.6× as long.

Decision: -ngl 99 --n-cpu-moe 40 -ub 4096 -fa on -t 10, KV f16, 128k context, one slot. A smoke test with a 12.5k-token tool prompt took 14.0 s cold and 2.3 s for the second request, both with correct tool calls.
