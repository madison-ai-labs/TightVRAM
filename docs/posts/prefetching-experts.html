Prefetching experts: +45 % prefill in 187 lines

Prefill spends 59 to 65 % of its time uploading experts, and llama.cpp does that strictly before computing each layer. Loading the next layer's experts on a second CUDA stream gave +37 to +50 %, with bit-identical output. It's now in production.

Upload, then compute, then upload

We read the scheduler in build 45b6604b2. ggml_backend_sched_compute_splits copies each split’s inputs first, with host-resident weights last, which calls sched_copy_experts. Only then does the split run with graph_compute_async, on the same backend and the same CUDA stream. The upload for layer L+1 can’t start until layer L has finished computing. On top of that, sched_copy_experts reads the router’s ids back to the host with a synchronize, once per layer, to find out which experts to upload.

A first estimate from bandwidth alone: pinned host-to-device measures 12.4 GB/s (256 MiB, 20 copies × 3 runs, and 12.1 GB/s in 640 KiB chunks the size of one expert matrix). 19.7 GB of experts per micro-batch gives ~1.59 s of upload. A pp4096 micro-batch takes 2.22 s with pinned memory and 2.62 s with mmap. Subtract the upload at each mode’s own rate and both leave almost exactly the same rest, 0.63 and 0.69 s. Upload and compute add up, and the whole dio gain is explained by the faster transfer.

Measuring it properly

To stop guessing, we built a profiling variant of the production binary (patch: timers in compute_splits with explicit synchronizes, a separate graph view for the first MUL_MAT_ID node of each split, and per-tensor byte counts in sched_copy_experts). The timers cost 0.5 % throughput. We ran real text, not random tokens, through llama-server with the exact production arguments:

Profile Prompt ms per 4k batch Upload Expert compute Attention etc. Upload share H2D rate
mmap 4,096 2,963 1,912 322 649 65 % 9.9 GB/s
mmap 65,536 3,258 1,923 315 931 59 % 9.9 GB/s
dio (pinned) 4,096 2,597 1,545 320 653 59 % 12.3 GB/s
dio (pinned) 65,536 2,885 1,547 315 933 54 % 12.3 GB/s

Expert math is only 10–13 % of prefill. 12.3 GB/s is effectively the ceiling of PCIe 3.0 x16, and the link reports pcie.link.gen.max 3, so the transfer can’t get any faster on this board with this CPU.

Random tokens lie here. With real text, a 4096-token batch uses on average 98 % of the 256 experts per layer (minimum 90 %). With llama-bench’s random tokens it’s 85 %, which is why llama-bench reports 10 % more prefill than the server. For our purposes, real text means you can upload all experts of the next layer without knowing the routing. That costs only 2–6 % more bytes.

What overlap could be worth

A per-layer model built from these measured parts:

Strategy dio 4k dio 16k dio 64k
A: reorder within a layer (upload up/down while gate computes) +8 % +8 % +7 %
B: load all experts of layer L+1 on a second stream while L computes +43 % +46 % +48 %
C: like B, but only the experts actually used (oracle) +46 % +54 % +50 %

Reordering inside a layer is pointless, because there’s too little expert compute to hide anything behind. Routing prediction is pointless too: the oracle barely beats “load everything”. What’s left is B, at the cost of a second buffer for one full layer of experts (~0.5 GB). Even with B, prefill stays upload-bound in the 30 DeltaNet layers (39 ms upload against 21 ms compute). Only the 10 full-attention layers at long context have enough compute to hide the upload completely.

Someone had already written it

A branch by thecodacus (prefetch-experts, 5e7f627) implements B for an older llama.cpp. Upstream has since moved the input copy into ggml_backend_sched_copy_input. We ported the logic with a script into our build: +187 lines, only in ggml-backend.cpp, enabled with GGML_SCHED_PREFETCH_EXPERTS=3 (3 slots). Without the variable the binary behaves exactly like the production build (1,643 / 1,629 / 1,418 t/s against 1,637 / 1,630 / 1,422).

  • dio: +45 / +50 / +45 / +37 %. That’s exactly where the model put it. The gain at 120k is smaller because attention takes a larger share there.
  • mmap: +37 / +41 / +40 %. This answered an open question: uploads from pageable memory do overlap with kernels on a second stream. The gap to pinned stays at ~20 % (9.9 vs 12.3 GB/s).
  • Output is bit-identical. 64 generated tokens at temperature 0 gave the same text in all pairs, and the top-10 logprobs matched with a maximum |Δ| of 0. Prefetch only activates when n_used · n_tokens ≥ 2 · n_expert, so it’s off during generation.
  • Cost: +630 MiB of VRAM (3 slots × the largest expert tensor). At 128k context with pinned memory the peak is 7,793 of 8,192 MiB, about 0.4 GB free. Tight, but stable, including at 120k and 130k tokens.

Doubling the micro-batch

With the upload hidden, a bigger micro-batch amortizes the remaining fixed cost. But ub 8192 doesn’t fit at 128k context:

ub Context Starts? Compute buffer that fails
4096 131,072 yes
6144 131,072 no 2,978 MiB
8192 131,072 no 3,842 MiB
8192 65,536 yes
12288 65,536 starts, crashes on the first request

At 64k context, the combination of pinned memory, ub 8192 and prefetch reaches 3,590 t/s at 16k tokens: 2.2× pinned memory without prefetch, and 2.6× the mmap profile that was in production that morning. At 64k tokens it’s 2,768 t/s.

What’s in the compute buffer

Why does ub 8192 need 3.8 GB at 128k context? We patched ggml-alloc.c to dump all live tensors at every new peak. The dump is planned before cudaMalloc, so it also covers the configurations that fail, and its peak matched the failing allocation to the byte (2,978.05 and 3,842.06 MiB).

ub Context Peak KQ mask MoE down + weighted Activations Gaps
4096 65,536 1,602 512 256 + 256 96 482
4096 131,072 2,114 1,024 256 + 256 96 482
8192 65,536 2,818 1,024 512 + 512 192 578
8192 131,072 3,842 2,048 512 + 512 192 578

MiB, at the peak of the prefill graph.

  • The KQ mask is the biggest single item. It’s one f16 tensor attn_inp_kq_mask of shape n_kv × n_tokens, live across the whole graph, and the reserve sizes n_kv at the full context. At ub 8192 and 128k, that’s 2 GiB just for a mask that is mostly zeros and minus infinity.
  • Second item: ffn_moe_down and ffn_moe_weighted sit side by side at f32. The multiply could run in place, but the allocator doesn’t reuse the parent here. We haven’t found out why yet. In place would save up to 512 MiB.
  • Without the mask, ub 8192 needs ~1,794 MiB, less than ub 4096 needs at 128k today. That’s calculated from the measured parts, not tested.

A fork by stew675 derives the mask on the fly instead of storing it. That saves 2 GiB exactly, with an estimated 2–4 days to port. It has two catches for us: with an image in context it falls back to the dense mask (M-RoPE), and on NVIDIA it lacks the causal tile skip.

And with a different CPU?

The board is a Z590, which supports PCIe 4.0 at the GPU slot, but only with an 11th-gen CPU. With prefetch the compute is almost fully hidden, so prefill now scales with the link. At an assumed ~24 GB/s on Gen4, the upload per micro-batch would halve, and pp4096 would land around 4,000–4,500 t/s instead of 2,384. That’s an estimate, and there’s no budget for it.

Decision: in production since 25 November, 23:08, as a new build next to the old one (rollback is one symlink). The default profile uses pinned memory, ub 4096, 128k context and prefetch. A second profile with ub 8192 at 64k is installed for long prompts and gets switched by hand. Stability tests passed for random lengths up to 130,000 tokens, prefix reuse, tool calls, images and concurrent requests. Not yet tested: hours of sustained load. RAM is now the scarcer resource: 26.6 GB in use, 4.8 GB available after the test.
