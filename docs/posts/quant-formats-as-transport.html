Quant formats as a transport problem

We quantized real expert tensors of Qwen3.6 into 30 formats and measured error, CPU decode time, GPU time and upload cost for each. On this machine the right question isn't "how many bits" but "how many bytes per millisecond of unpacking".

The idea

A quant format is usually treated as a property of the model file. On a machine where the same expert weights are read by the CPU during generation and pushed over PCIe during prefill, it’s really a transport format. The cost is bytes divided by bandwidth, plus the time it takes to unpack them, and that second part differs a lot between formats.

Setup

  • Real tensors: experts of layers 5 and 20 (gate, up, down, 256 experts each) in BF16, fetched with HTTP range requests from the original Unsloth repository into a sparse file.
  • Quantized with ggml and Unsloth’s importance matrix, per expert, exactly as llama-quantize does it. As a check of the harness, Q4_K with the imatrix reproduces the shipped UD-Q4_K tensors exactly (0.06814 = 0.06814 for layer 5 gate).
  • Error: activation-weighted relative error sqrt(Σ in_sum2·ΔW² / Σ in_sum2·W²) over the calibration tokens. Without the weighting, the shipped file and a naive Q4_K would look equal, so the metric has to be weighted. This is a diagonal approximation, not a KL divergence.
  • Time: MUL_MAT_ID for one token, 8 random experts of 256, 10 threads, 300 repetitions, median, scaled to 40 layers. Only the MoE part of the network is counted.
  • “A+B” formats are a base plus a quantized residual, like Q4_K plus a Q2_K correction.

What stands out:

  • The i-quants are compute-bound on AVX2. IQ3_S has the bits of Q3_K and is slower than Q4_K. IQ1_M at 1.75 bpw is slower than Q3_K. For the CPU path on this machine, the K-quants win at every size below 5 bits.
  • Base-plus-residual formats don’t pay on the CPU. Q4_K + Q2_K reaches Q6_K-like error at more bits and more time. The second dot product costs more than the bytes it saves.
  • Q3_K versus the shipped Q4_K: −21 % time in the MoE part, at about twice the weighted error. The calibration in the previous post says that time saving really shows up in tokens per second (s ≈ 0.83–0.91).

The GPU side: prefill with uploads

For a 4096-token micro-batch, per layer, with experts uploaded from pinned memory:

Format GPU compute + upload, serial Overlapped Prefill, MoE only, serial → overlapped
Q8_0 8.5 ms 77.4 ms 68.9 ms 1,323 → 1,487 t/s
Q6_K 8.1 ms 61.3 ms 53.2 ms 1,671 → 1,926 t/s
Q4_K 7.3 ms 43.8 ms 36.5 ms 2,340 → 2,807 t/s
Q3_K 7.5 ms 35.4 ms 27.9 ms 2,894 → 3,675 t/s
IQ2_XXS 6.8 ms 23.5 ms 16.7 ms 4,351 → 6,123 t/s

On the GPU every format computes in 7–9 ms per layer, and uploading the experts takes 4–9× as long. Prefill is an upload problem, which is what the prefetch post is about. These numbers cover only the MoE part, so they’re upper bounds.

And the SSD?

The NVMe drive peaks at 3.58 GB/s with O_DIRECT (2 threads, 4 MiB blocks). If experts came from disk instead of RAM, a token would cost 158 ms at Q4_K and 121 ms at Q3_K: 6–8 tokens per second. With 32 GB of RAM and a 22 GB model, the SSD isn’t on the hot path, and we confirmed it: under load, the server had 6 major page faults per minute and read 0 bytes.

Status: open. Q3_K experts are the largest remaining single lever, on both sides: fewer bytes for the CPU in generation and fewer bytes over PCIe in prefill. The next step is Unsloth’s UD-Q3_K_XL with a proper KL divergence test against Q8_0 and our tool-use test.
