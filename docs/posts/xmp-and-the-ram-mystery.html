XMP, and the RAM bandwidth that wasn't

Turning on XMP gave 15 to 24 % more tokens per second. Then STREAM claimed the RAM got slower with more threads, and the explanation turned out to be the CPU's clock control, not the memory.

XMP: the cheapest win of the project

The RAM had been running at JEDEC defaults since the build: DDR4-2133. The sticks are rated for 3000. We switched on XMP II in the BIOS (full profile, no motherboard sub-timings, multi-core enhancement untouched), ran memtester over 20 GB without a single error, and repeated every benchmark with the same build, the same model files and the same configurations.

  • Prefill +16 to +20 % in all eight configurations, very evenly.
  • Generation +15 to +24 %, with one outlier at +5 %.
  • The 9B control, entirely in VRAM, moved by at most 2 %. That’s what you’d expect if the change is really the RAM.

Then STREAM said something impossible

Our RAM benchmark (a STREAM-like OpenMP kernel, 3 × 1 GiB arrays) showed this:

STREAM, XMP on 1 thread 10 threads 20 threads
Copy (GB/s) 18.8 14.0 14.2
Triad (GB/s) 22.4 13.1 13.6

More threads, less bandwidth. XMP improved single-thread numbers by 25 % and the 10-thread numbers by nothing. Two readings were on the table: the memory system is saturated by a single core (a real limit), or the measurement is broken.

Neither was true. Under pure memory load on many cores, intel_pstate with the powersave governor and EPP balance_performance drops core and uncore clocks to roughly 800–1200 MHz. With the governor set to performance, the same test reaches more than twice the bandwidth:

Measurement powersave performance
likwid-bench load, 10 cores 17.7 GB/s 37.7 GB/s
STREAM triad, 10 threads 13.1 GB/s 23.3 GB/s
Clocks during STREAM (core / uncore) ~1170 / ~875 MHz 4800 / 4300 MHz
Qwen tg128 37.0 / 37.2 37.8 / 37.4
Qwen pp16384 1513 / 1512 1486 / 1495

A/B/A/B, only the governor changed, two rounds each.

37.7 GB/s is 79 % of the theoretical 48 GB/s for dual-channel DDR4-3000, so there’s no hardware problem. And the inference doesn’t care: +1 % for generation, −1.5 % for prefill, in the same direction in both rounds. During generation the CPU isn’t idle enough for the governor to clock it down. The governor stays on powersave.

The consequence for everything published before this: every multi-threaded STREAM number above measured the clock control, not the RAM. “XMP changes nothing at 10 threads” is not a statement about memory.

Bytes per token: the prediction held

If generation is bound by RAM bandwidth, the bytes per token should be predictable from the model file. From the GGUF header: 18,760 MiB of routed experts, 256 per layer, 8 active. 8/256 of that is 615 MB per token.

Measured with the memory controller counters (perf and likwid-perfctr agree): 37.19 t/s at 23.2 GB/s of DRAM reads, so 624 MB per token, 1.5 % above the estimate.

23.2 GB/s is an average over the whole token, including the part where the GPU works and the CPU waits. The GPU sat at 25 % utilization during tg. That puts the CPU phase at about 20 of 27 ms per token, which means roughly 30 GB/s while the CPU computes experts, or 80 % of the measured peak. RAM bandwidth is the main limit for generation. We’re moderately sure about that: it’s inferred from GPU utilization, and nobody has measured the rate inside the CPU phase directly.

Threads: six are enough

-t tg128 (two rounds) DRAM read during tg MB per token
2 24.3 / 24.6 15.3 GB/s 626
4 33.3 / 33.7 21.0 GB/s 626
6 35.9 / 36.0 22.6 GB/s 628
8 36.3 / 36.8 23.0 GB/s 628
10 36.7 / 37.1 23.1 GB/s 625

Bytes per token stay constant, and threads only change how fast they arrive. Generation saturates at about 6 threads. Prefill doesn’t depend on -t at all. Also tested, without effect: --threads-batch 4/10/20, and pinning to the 10 physical cores with --cpu-mask 3ff --cpu-strict 1.

Noise lives in the process, not in the repetition

While chasing ±2 t/s differences, we found the most useful methodological fact of the project. Within one llama-bench process, the 5 repetitions sit within a few tenths of a token per second. Between processes with identical parameters, tg ranges from 30.0 to 37.3 t/s.

Six alternating processes, tg128 Values (t/s) Median
free 32.7 / 37.0 / 36.2 / 36.2 / 37.1 / 35.0 36.2
pinned to cores 36.2 / 36.8 / 37.3 / 33.5 / 32.4 / 33.8 35.0

We haven’t found the cause. SMT placement is ruled out because pinning scatters just the same. The rule we’ve used since: compare tg only across several separate processes, and treat differences under ~3 t/s from single runs as nothing. The ± printed by llama-bench understates the real uncertainty by an order of magnitude.

A correction

An earlier commit called the bandwidth question “solved” and claimed the clock speed played no role, that row-buffer effects explained the numbers, and that tg had a ceiling of 38 t/s. All three were wrong. The clock had only been checked during the tg phase (where it sits at 4300 MHz). The ceiling was circular reasoning. The lab notes keep the wrong version and the correction next to each other, and so does this post.

Decision: XMP stays on. Governor stays on powersave. -t 10, no pinning, default batch threads.
