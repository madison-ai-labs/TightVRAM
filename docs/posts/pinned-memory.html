Pinned memory: --load-mode none, auto and dio

Switching the expert weights from a memory-mapped file to pinned memory made prefill 17 % faster and explained the mystery writes from the day before. It also brought swap bursts, a crash at 115k tokens, and a lesson about MemAvailable.

The mystery from day one

The memory controller counters had shown that each prefill micro-batch reads 1.5–1.7× the size of all experts and writes about half as much. Inference shouldn’t write much of anything. The pattern looked like a copy into a staging buffer, but we hadn’t read the code yet.

What the code says

In build 45b6604b2, when the model is loaded via mmap (--load-mode auto, the default), the loader replaces the host buffer type with plain CPU memory. The experts then live in the page cache as an ordinary mapped file. With --load-mode none they go into CUDA_Host buffers: pinned memory allocated through the CUDA driver.

Op placement is identical in both modes. In both, sched_copy_experts uploads only the experts that are actually used, directly from the weight tensor with cudaMemcpyAsync. llama.cpp itself copies nothing in between. The only difference is pageable versus pinned memory. Copying from pageable memory forces the driver to stage the data through its own pinned buffer: read from the source, write to staging, DMA reads staging. Hence reads of about 2× and writes of about 1×.

Prediction before the run: with pinned memory, writes ≈ 0 and reads ≈ 16.5 GB per ubatch. Measured: writes −0.4 to 5.0 GB (noise around zero) and reads 17.0–18.2 GB.

The numbers

12 separate llama-bench processes in ABBA BAAB ABBA order, 5 repetitions each, nc 40, ub 4096:

auto (mmap) none (pinned)
pp512 341.6 450.0 +31.7 %
pp4096 1,561 1,845 +18.2 %
pp16384 1,517 1,781 +17.4 %
tg128 37.0 36.8 none
RAM read per ubatch 33.5 GB 17.6 GB halved
RAM written per ubatch 16.6 GB ≈ 0 gone
Load time, warm 1.7–1.9 s 16.3–20.4 s +16 s

The gain is a fixed 0.36–0.40 s per ubatch, which is why short prompts gain more in percent. Generation doesn’t change, as predicted: the CPU computes experts in place, and nothing is copied.

In a real workload

Benchmarks with random tokens are one thing. We built a replay of real usage: an interactive chat, a 6-turn coding agent with tool calls, 32k and 64k documents, the agent again warm, a second agent, chat again. 36 requests per server instance, instances in the order auto none none auto, with identical context lengths, output lengths and tool calls in every run.

About 10 % less wall time for everything with long prompts. Nothing for short chat questions.

Then it got complicated

Pinned memory doesn’t count as available in /proc/meminfo. With auto, the 20.8 GiB of experts sit in the page cache and count as available even though they’re needed. With none they’re shared memory and don’t. MemAvailable showed 23 GiB under auto and 3.8 GiB under none for essentially the same working set. The real difference: under memory pressure, auto re-reads the file, and none has to swap.

And sometimes it swapped. In 2 of the first 4 none instances, the kernel unmapped most of the pinned pages right after loading (RssShmem dropped from 20 GiB to 2.5–6 GiB) and pushed a few hundred MiB of the server’s anonymous memory into swap. One instance got a 2.75 s time-to-first-token instead of 0.7 s. Then, on a 115k-token document:

none, instance 2 none, instance 3
115k document, prefill 89.9 s (1,276 t/s), −11 % vs auto aborted after ~4 s
Swap-out since load 0 1,563 MiB in ~4 s
Inactive(file) at “ready” 8,917 MiB 2,855 MiB
Inactive(file) at the abort 30 MiB

The watchdog killed instance 3 at our 1 GiB swap limit. MemAvailable was 7 GiB at the time and MemFree above 2 GiB, so this wasn’t a lack of memory in the usual sense. The inactive file list ran empty while 4.3 GiB of the GGUF stayed on the active list, and reclaim went after anonymous and shared memory instead.

dio: pinned, without the page cache

--load-mode dio reads the file with direct I/O into the same pinned buffers and leaves the page cache nearly empty (~9 GiB truly free instead of ~0.4 GiB). We ran 40 instances in randomized blocks (none warm, none with the GGUF evicted, dio warm, dio cold), then 10 more under realistic load, then three back-to-back none instances to test the “previous instance” theory.

auto dio
Load 1.8 s warm, 8.3 s cold 14.0 s
Agent, cold 34.7 / 35.3 s 31.0 / 31.2 s (−11 %)
Agent, warm 23.5 / 23.8 s 21.3 / 21.4 s (−10 %)
Document 64k, prefill 51.0 / 50.8 s 44.7 / 44.7 s (−12 %)
Document 115k, total 104.2 / 104.8 s 93.4–93.5 s (3 of 3)
Follow-up turn, time to first token 2.39 s 2.00 s
MemAvailable, minimum 22.7 GiB 3.7 GiB
Swap bursts 0 of 25 instances

Zero bursts with dio, but also zero of 13 for none since then. The burst didn’t reproduce, so we can’t claim dio prevents it. What’s measured: dio keeps the full prefill gain of none, costs 1.5 s more load time than none, and leaves the page cache small. Its cause remains open.

A 55-minute soak test with dio (504 requests, every prompt with its own nonce) showed no growth at all once the prompt cache had filled: VRAM flat at 7,141 MiB, RSS flat, prefill 1,501 / 1,501 / 1,500 / 1,501 t/s per quarter. An issue on GitHub reported context checkpoints piling up in VRAM. In this build they live in host RAM (std::vector<uint8_t>), and VRAM didn’t grow over 36 or 504 requests.

Decision, in two steps. On 6 November: dio is the best option for pure inference, but it locks 20 GiB permanently, so the default stayed auto while the machine was also used for builds and benchmarks. On 25 November dio became the default as part of the prefetch profile. Since then RAM, not VRAM, is the scarcer resource on this machine.
