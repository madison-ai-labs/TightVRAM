gpu-unlock: +90 % on GEMM, +1 % on tokens

A boot-time firmware exploit lifts the RTX 3070's halved tensor-core rate for FP16 with FP32 accumulation. Matrix multiplies got almost twice as fast. Our quantized LLM barely noticed, and image generation got 14 to 32 % faster.

What it is

GeForce cards run FP16/BF16/TF32 tensor-core math with FP32 accumulation at half the rate the silicon can do. Zagitta/gpu-unlock (version 2.0.0, commit 7eb51bc) removes that limit. A kernel module in the initramfs runs before the NVIDIA driver, uses a buffer overflow in the signed booter to write the speed selectors, and then resets the function (FLR). Without the boot parameter gpu_unlock.targets= the module does nothing.

That’s a firmware exploit in the boot path of a remote machine with no hardware watchdog. We wanted a number that would justify it.

Setup

Four fresh boots, A1 B1 A2 B2, same initramfs. The kernel command lines differ only in gpu_unlock.targets=0000:01:00.0. Same build, same driver, same 270 W power limit, same server profile. Values are medians per boot, and Δ compares the mean of A1/A2 with B1/B2.

The unlock works: +85 to +90 % on GEMM, FP32 unchanged, and A2 falls back to stock after the reboot. For our profile it does almost nothing: 0 to 1.3 % without depth, 5 % at 115k. The spread between A1 and A2 was at most 1.1 %, so these are real but small. Even the 9B model, which never touches system RAM, gained only 0.6 %, so RAM isn’t the only reason.

Upstream’s explanation, which our curve matches but which we haven’t verified in the ggml source: quantized GGUF weights run in INT8 kernels, and only FlashAttention over the f16 KV cache benefits. That’s why the gain grows with context depth.

Outputs were identical: fixed-nonce requests produced the same text hash in all four boots.

Where it does matter: image generation

We had a second workload on the same card: Z-Image-Turbo in ComfyUI generating coloring-book line art. Same 72 images and seeds, one fresh warm boot per arm:

All 72 images came out pixel-identical to the first run in both arms. The full batch went from 12:53 to 10:36 min (−18 %). bf16 gains the most (−32 %), but even with the unlock it stays slower than int8 and didn’t look better. The card sits at its 270 W limit in both arms and throttles thermally in 15 % of the samples with the unlock versus 8 % without.

Stability: thin evidence

Three unlock boots, about 35 minutes of load in total, no Xid errors, no lockups. All three were warm boots. Upstream issue #137 reports a hard lock in 1 of 5 boots on a Gigabyte 3070 LHR, on a cold start, which we haven’t tested.

Testing the safety net was also instructive. hardlockup_panic=1 isn’t a boot parameter this kernel knows, so the test entries wouldn’t have rebooted a hard-locked machine by themselves. Only softlockup_panic and panic=10 took effect. The test entries now use nmi_watchdog=panic,1, which sets kernel.hardlockup_panic to 1. A real hard lock hasn’t triggered it yet. What is reliable is the way back: the one-shot boot entry falls back to the default (no unlock) after any reset.

Decision: the unlock stays off. 5 % on very long documents isn’t worth a firmware exploit in the boot path of a machine nobody is sitting next to. The package stays installed but inert: it costs a 153 MB instead of 65 MB initramfs and a tainted kernel, and DKMS rebuilds it for new kernels. We’ll look again if unquantized FP16/BF16 workloads or LoRA training show up.
