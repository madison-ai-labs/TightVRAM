Where generation time goes

From the earlier posts: one token takes ~27 ms. About 20 ms of that is the CPU reading 615 MB of experts from RAM, and about 7 ms is the GPU. The GPU part reads 2,039 MiB of weights per token at 448 GB/s, which is ~4.8 ms in theory and ~5.5 ms in practice. That leaves at most ~1.5 ms for synchronization and kernel launches. Generation speed is decided in the CPU phase.

An external analysis suggested five levers: predict and preload experts, cache experts, speculate (MTP), drop the weakest experts, or quantize experts lower. Preloading only helps if experts are streamed, and in generation they aren’t. A byte over PCIe 3.0 costs 2.4× as much time as a byte the CPU reads from RAM. The LRU cache already lost. What remained was a fixed set of hot experts on the GPU, plus MTP.

Tracing the router

We wrote a small tool on top of llama.cpp’s eval callback that runs a prompt and records, for every layer and token, which 8 experts the router picked and with what weight. Six prompts covering agent tool use, 14k tokens of C++ source, new code, German documentation, English chat and a code review: 43,335 tokens, 3,844 of them generated.

The first run produced garbage, for two reasons worth knowing if you try this yourself. ffn_moe_topk is a view on the argsort result and isn’t contiguous, so it has to be read along its strides. And layer 39 only computes the output row during prefill (inp_out_ids), so it has to be excluded.

The routing is skewed. Within a layer, the top 5 % of experts get 31 % of the calls (12–47 % depending on the layer, flattest in early layers), and the top 10 % get 46 %. Reuse is high: 37.7 % of a token’s experts were used by the previous token, 66.5 % within the last 8 tokens. Uniform routing would give 3 %.

A fixed set of experts on the GPU, chosen from five prompts and tested on the sixth (leave-one-prompt-out, generated tokens only):

VRAM budget Uniform Leave-one-out In-sample tg estimate
800 MiB (free at 128k) 4.3 % 18.4 % 39.5 % 42.9 t/s (+16 %)
1,024 MiB 5.4 % 21.7 % 44.4 % 44.1 t/s
2,600 MiB (≈ free at 64k) 13.9 % 37.9 % 67.0 % 51.5 t/s (+39 %)

In-sample is about twice leave-one-out, so which experts are hot depends strongly on the prompt. A set that adapts at runtime should land between the two.

Simulating the fork

A llama.cpp fork (llama-wackMall, grown out of closed PR #26563) does exactly this: it keeps a heat map per layer and swaps hot experts into GPU slots while generating. We read the code first and found that tiering applies to micro-batches of up to 16 tokens, so an MTP verify of 2–3 tokens would also go through it. Swaps are synchronous, at most one per layer per update, with hysteresis.

Then we replayed its exact policy on our traces, including the cost of each swap (1.83 MiB at 12.4 GB/s = 0.155 ms):

Budget Slots per layer Fixed (leave-one-out) Seeded + adaptive Empty + adaptive Swaps per token tg estimate
800 MiB 10 18.1 % 19.6 % 25.7 % 0.66 45.5 t/s (+23 %)
2,600 MiB 35 39.1 % 41.2 % 50.1 % 2.46 57.6 t/s (+56 %)

Swap costs were negligible at 0.1–0.4 ms per token. Starting from a heat-map seed was worse than starting empty, because the large seeded scores never let the hysteresis swap anything. The author’s own figure of ~50 t/s on a 3070 fell between our rows. Everything looked consistent.

Measuring it

Production server stopped, the card claimed, three prompts per process, temperature 0, arms in the order ABCDDCBAABCD, three processes per arm. The rule was written down before the run: a winner needs a median of at least 1.15× baseline and a minimum above the baseline’s maximum.

C, the tiering fork, came out 4.3 % slower instead of 23 % faster. The tiering itself was running (10 slots/layer, 0.79 GiB pinned). Its reported hit rate of 23 % turned out to be counted over prefill tokens too: we recomputed (9,336 prompt + 1,096 generated) × 8 × 40 = 3,338,240, which matches the reported total of 3,338,560. In a later run with almost only generation, the fork’s own counter showed 26.2 % against our simulated 25.7 %. The simulation of the hit rate was right. The hits just didn’t turn into speed.

Why not? A later arm F, the same fork with tiering disabled, ran at 32.85 t/s, −5.6 % against our build. The fork’s base is 2,002 commits older than ours and slower on its own. With tiering on, it wasn’t slower than without. Tiering costs nothing and gains little.

The fork also forces a micro-batch of 256 for prefill, which made prompt processing 3.5–9.6× slower:

Request A (our build) D (fork + MTP)
Agent with tools 11.7 s 19.1 s
New code 12.0 s 10.7 s
Code review 16.9 s 65.5 s

MTP: real gain, still out

Qwen3.6 has a multi-token-prediction head. Our build supports --spec-type draft-mtp, and reading the code showed something important: unlike n-gram speculation, MTP does not replay on rejection. It keeps a snapshot of the recurrent state per token and rolls back. That moves the theoretical break-even from ~73 % to ~46 % acceptance.

First attempt on our build: out of memory. The draft context allocates its own compute buffer at the same ubatch of 4096 (1,344 MiB, ~8.5 GB in total). The fix is --spec-draft-n-ubatch 256. Second window, rules again fixed in advance, with the decision made on the arm that uses the production sampler:

Arm tg median vs A Acceptance
A: production profile 34.79 t/s
MTP, greedy 39.70 t/s +14.1 % 0.851
MTP, production sampling 38.68 t/s +11.2 % 0.830
Pre-registered criterion Result

min(MTP) > max(A) met: 38.32 > 35.26

The generation gain is real and deterministic: draft counts and tokens were identical across processes. But the draft context reads the prompt too, at ubatch 256, and that costs 22 % prefill on a 32k document. For agent work, where requests read far more tokens than they write, the prefill loss outweighs the generation gain.

The useful by-product

The same window calibrated how generation time scales with expert bytes, by forcing the model to use fewer experts per token (expert_used_count 8 → 6 → 4):

Experts per token ms per token Scaling factor s
8 28.30
6 23.93 0.83
4 18.74 0.91

s = 1 means time scales perfectly with bytes, and s = 0 means it’s all fixed per-op overhead. At 0.83–0.91, expert bytes are what costs time. That makes smaller expert quants the most promising remaining lever for generation. See quant formats as transport.

Decision: don’t port the tiering, because the fork’s base is slower and tiering gains little on top of it. MTP stays out of the production profile: +11 % generation doesn’t make up for −22 % prefill and a VRAM peak that broke our own limit. Next lever: Q3_K experts.
