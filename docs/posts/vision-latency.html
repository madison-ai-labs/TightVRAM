Why a screenshot takes 12 seconds

Qwen3.6 reads screenshots fine with its vision projector on the CPU, but a 1280-pixel image costs 12 seconds before the first token. 81 % of that is the image encoder. On the GPU it takes 0.5 s, and it costs half the context.

The projector doesn’t fit next to the model

The vision projector (mmproj-F16, 858 MiB) doesn’t fit on the GPU next to the model with 128k context. With it on the GPU, the server crashes at startup with cudaMalloc failed: out of memory in clip_model_loader::load_tensors, and systemd restarts it in a loop. On the CPU (--no-mmproj-offload) it works: text in a synthetic screenshot was read correctly, word for word, including a path:line:column and an amount in euros. It cost ~1 GB of RAM and no VRAM.

Request Image tokens Prefill Total
JPEG scaled to 1280 px 1,033 12.1 s 14.6 s
Follow-up question, same conversation 24 new, 1,117 cached 0.3 s 2.1 s
PNG at full Retina size 2560 × 1600 4,033 85.9 s 88.5 s

The prompt cache works with images: a follow-up doesn’t re-encode the picture. Downscaling is mandatory: full Retina resolution costs 4× the tokens and 7× the time.

Where the 12 seconds go

The build only logs image timings at -lv 4. We timed the encoder from journal timestamps and cross-checked against a -lv 4 profile (0.07 s apart). Every cold measurement used unique file bytes, so nothing came from cache.

The levers

Variant 1280 px 2560 px Quality Cost
Projector F16 on CPU, -t 10 11.82 s 84.46 s reference
Projector Q8_0 on GPU, 64k context 2.77 s 8.32 s same half the context
Q8_0 on CPU ~12.3 s ~91 s same 5–8 % slower
--image-max-tokens 768 8.42 s 8.42 s small print worse server downsizes
--image-max-tokens 512 5.38 s 5.37 s tables fine, small print breaks
--image-max-tokens 256 2.94 s 2.91 s useless for OCR

On the GPU, the Q8_0 projector at 64k context started cleanly in 2.2 s and left at least 1,267 MiB free. Our prediction of 28 MiB per 1,024 tokens of context was off by 1 MiB. Thread counts of 6, 16 and 20 were all slower than 10.

How small can the image be?

The model transcribed a ladder of 48 random tokens printed at decreasing sizes, plus code, an error message and a table:

Image Random ladder Code probes Error message Table
2560 PNG 46 / 48 7 / 9 7 / 8 10 / 10
1280 JPEG 31 / 48 6 / 9 8 / 8 10 / 10
1024 JPEG 16 / 48 6 / 9 7 / 8 10 / 10
768 JPEG 7 / 48 4 / 9 4 / 8 10 / 10
512 JPEG 1 / 48 0 / 9 0 / 8 9 / 10

Up to 1280 px it reads prose, tables and error messages almost perfectly. Random strings need an effective font size of 9–10 px. At 512 px it invents plausible code instead of saying it can’t read it. l1I| and "O0" it never gets right at any size. An unscaled 1024-pixel crop reads as well as the full 2560 px image, at 640 tokens.

Warming up the cache: only one shape works

Shape of the real request Cached tokens Prompt time
Cold, image + question 0 11.85 s
Pre-sent user[image], then image + question in the same message 0 11.8 s
Pre-sent user[image], then [assistant: pre-answer] [user: question] 1,014 0.38 s

The server doesn’t create a checkpoint after an image chunk, and the hybrid model’s recurrent state can’t be rolled back. So the cached prefix must end exactly after the image turn. A foreign text request in between (120 to 27,800 tokens) didn’t evict the image: the RAM cache brought it back in 0.05–0.1 s.

Two operational surprises. A client that disconnects after 3 s doesn’t free the slot, which stays busy until 11.76 s. And a short text request arriving while an image is being encoded waits 12.4 s instead of 1.6 s.

Text instead of the image?

We also tried sending Apple Vision’s OCR text instead of the picture:

Variant Correct (of 20) Time to first answer
Image, 1280 px 17 11.9 s
OCR text only 11 1.8 s
OCR text + 512 px image 14 3.9 s

OCR errors come through even with the small image alongside it: 101 instead of 10 l, a dropped umlaut. Diagrams with text only: 0 of 4, because the arrows are gone.

Decision: the projector stays on the CPU, so the server keeps 128k context. What follows for clients: downscale to 1280 px, send a crop when you can, and pre-send the image as its own turn while the user is still typing. The GPU projector at 64k is a documented option for image-heavy sessions.
