The thinking loop that wasn't a loop

A coding agent thought for 15 minutes and 32,894 tokens without calling a tool. 280 replays of that first step later, the endless loop turned out to be rare, and the model card's coding sampler halved the long tail.

What happened

A coding agent on our server spent its whole 900-second lease on the very first step: 32,894 tokens of thinking, zero tool calls. Qwen3.6 went in circles (“Wait, …”, “Self-correction”, “Let’s go.”) with almost no literal repetition, so repetition penalties had nothing to grab onto.

The sampling up to then was llama-server’s default: temperature 1.0, top_k 20 and top_p 0.95 (taken from the GGUF), plus the server’s own defaults min_p 0.05 and presence penalty 0.

What the sources say

  • Qwen’s model card, thinking mode, general tasks: T 1.0, top_p 0.95, top_k 20, min_p 0, presence 1.5. Thinking mode, precise coding: T 0.6, top_p 0.95, top_k 20, min_p 0, presence 0. The card adds that presence between 0 and 2 dampens endless loops, and that high values occasionally cause language mixing.
  • Unsloth’s docs set presence 0 for both thinking cases and 1.5 only without thinking.
  • The GGUF carries temp 1.0, top_k 20 and top_p 0.95, but no min_p and no presence.

The experiment

We replayed the exact first step of the agent (same system prompt, same tool definitions, same user prompt) with thinking on and max_tokens 4096, directly against the production server, with the arms alternating. In the second series a small wrapper only sent when the slot had been idle for 5 minutes, because another client was running 92k-token contexts on the same slot.

What it shows

  • The endless loop is rare. 1 of 120 with the old sampling. On the day it happened it had been 1 of 8, which was bad luck at small n. Whether T 0.6 prevents the loop, this data can’t say (0 vs 1).
  • The shorter tail is real. Half as many runs above 1,000 and above 1,500 tokens. A loop starts out as a long run. The direction is clear, the significance weak (23 vs 13 of 120).
  • Presence 1.5 is worse in thinking mode: the longest tail of the three. “Use presence 1.5 against loops” is true for the card’s general recommendation, not for this case.
  • Tool behavior didn’t change: the same first call, no broken arguments.

The decision rule was fixed before the second series: switch if limit hits don’t get worse, runs above 1,500 tokens don’t increase, and tool behavior stays the same. All three held.

Decision: --temp 0.6 --top-p 0.95 --top-k 20 --min-p 0.0 --presence-penalty 0.0 --repeat-penalty 1.0 for the coding profiles. Because clients don’t send their own sampling fields, this also applies to chat. The card recommends T 0.7, top_p 0.8 and presence 1.5 for chat without thinking. We haven’t measured that.

Deployed on 2026-11-26 in all coding profiles. The control run afterwards matched the old one: tool calling 81.5/84, boundaries 24/24, no broken calls, and screenshot transcription at 1280 px within run-to-run noise of the T 0 baseline.
