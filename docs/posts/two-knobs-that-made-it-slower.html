Two knobs that made it slower, and why

A VRAM cache for experts cut generation in half at a 0.07 % hit rate. N-gram speculation helped only when the answer repeated the prompt word for word, and it changed answers at temperature 0.

Both options sound like obvious wins for an MoE model with experts in system RAM. Both lost, and the reasons are more useful than the verdicts.

The VRAM expert cache: --moe-cache-mib

The idea: keep recently used experts in a VRAM cache so the hot ones don’t have to come from RAM. We expected no gain for generation, on the assumption that the CPU computes experts directly. Reading llama-moe-cache.cpp corrected that assumption before the run. With a cache budget set, batches up to 32 tokens no longer run on the CPU. They go through ffn_moe_slots and ggml_mul_mat_id on the GPU, which means every missing expert has to be uploaded first.

Three instances per budget in a Latin square, dio cold:

Budget Agent, total Hit rate, small batches Uploaded
0 31.2 s
128 MiB 46.9 s (+50 %) 0.00 % 522,449 MiB
256 MiB 46.0 s (+47 %) 0.07 % 548,316 MiB
512 MiB 45.6 s (+46 %) 1.60 % 540,586 MiB

Why: one token needs 40 layers × 8 experts = 320 experts, about 608 MiB. A cache smaller than one token’s working set evicts cyclically under LRU: by the time layer 1’s experts come around again, they’re gone. At 256 MiB that’s ~577 MiB of uploads per generated token, and generation goes from ~28 ms to ~61 ms per token. The extra 33 ms match a PCIe transfer at about 16 GB/s.

That doesn’t mean routing is random. A later routing trace found that 38 % of a token’s experts were already used by the previous token. The cache simply never had room for the reuse to show.

The outputs changed too: all answers were identical within a budget, but only 1–2 of 11 matched between budgets. Tool calls stayed valid. If you rely on reproducible outputs, don’t change the budget.

N-gram speculation: --spec-type ngram-mod

Speculative decoding without a draft model: when the recent output matches an n-gram in the context, propose the continuation and verify it in one batch. Ideal for code edits and JSON that repeat the input. Temperature 0, ABBAAB, 3 instances each:

Scenario Wall off Wall on Acceptance Output on vs off

Why the break-even is so high

Qwen3.6 is a hybrid: 30 of its 40 layers carry a recurrent state instead of a KV cache. You can’t just truncate a recurrent state when a draft is partly rejected. In this mode the server saves a checkpoint (62.8 MiB), and on partial acceptance it restores the checkpoint and decodes the accepted part again (spec_is_replay in server-context.cpp). A draft batch of ~64 tokens takes 0.82–0.84 s, and restoring takes 7 ms, so the cost is in the recompute.

From the counters: one draft costs ~1.1–1.3 s, a normal token ~28 ms. A 63-token draft has to land 40–47 tokens to pay for itself, so the break-even is at roughly 65–75 % acceptance. Even repetitive JSON missed it, because the changed values break every chain.

It changes answers at temperature 0

This is the more important finding. With speculation on, answers change wherever the text isn’t forced. In the warm agent run, all 6 turns diverged from the first draft on, with different tool calls (grep instead of read_file) and 445 instead of 359 tokens. Within one mode everything was reproducible (21 of 21 requests per mode identical across 3 instances).

Our hypothesis, not proven: the draft runs as a larger batch through a different kernel path, the logits differ numerically, and wherever the top two tokens are close the argmax flips. The same thing happened with the MoE cache. It would be testable by comparing n_probs logits for identical prompts.

Decision: both off. The MoE cache loses on this card with this model at every budget we could afford. N-gram speculation wins only on near-verbatim repetition, loses as soon as small changes appear, slows down agents, and makes outputs non-comparable.
